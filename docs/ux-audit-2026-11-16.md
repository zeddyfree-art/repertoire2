# Repertoire 2 — UX/UI and architecture audit (2026-11-16)

## Scope and confidence
Static code audit of the copied React/Vite repository on main. Reviewed app shell, Home, Build, Train, Tree, Play, settings, storage, Drive sync, styles, PWA manifest and CI. This is **not** a browser-based usability test or a complete accessibility/security assessment. Findings below distinguish directly observed implementation from UX hypotheses that require testing.

## Executive summary
The product has unusually deep functionality: opening repertoire construction, Lichess explorer, engine, move-tree visualization, spaced repetition, training, practice against Maia, game analysis, multi-profile support and backups. Preserve the underlying domain models and workflows. The most valuable change is **progressive disclosure and information architecture**, not cosmetic restyling alone.

**P0 — Before connecting Drive in the clone:** isolate the clone's cloud synchronization. The copied drive.ts still uses APP_KEY='repertoireApp', FOLDER_NAME='Repertoire app', and the same default OAuth client ID; sync.ts uses the same file discovery roles. Although browser storage is origin-scoped by path? **No:** localStorage and IndexedDB are scoped to origin, not path. Both /chess/ and /repertoire2/ are under zeddyfree-art.github.io, hence share localStorage and IndexedDB. gamesStore.ts explicitly uses createStore('repertoire-data','app'). This means the clone can open and mutate the **same local data** as the original, and potentially the same Drive files. Do not use the clone with live data before namespacing storage, Drive identity and caches and validating migration/backup behavior. Distinct GitHub repositories and URL paths do not isolate browser data.

## Findings (prioritized)

### P0. Data safety and app identity
- **Confirmed:** Both deployments share https://zeddyfree-art.github.io as their origin; path separation is not a storage boundary. Games IndexedDB uses database 'repertoire-data', store 'app'. Audit store.ts, caches, token keys, sync.ts META_KEY='drive-sync', drive.ts TOKEN_KEY='google-token' and CLIENT_OVERRIDE_KEY='google-client-id', version and install state. Create a v2 namespace for all app-owned browser persistence; do not accidentally auto-migrate old production data into the clone.
- **Confirmed:** Drive files are found by appProperties role tag (APP_KEY='repertoireApp'), not folder name alone. The clone currently targets the same logical Drive app and files. Give v2 distinct appProperties roles/key and separate folder; preferably default Drive sync OFF until verified.
- **Confirmed:** PWA manifest name remains 'Repertoire'; choose distinct display name/icon so both installs are distinguishable.
- **Recommendation:** Add automated isolation tests: legacy keys untouched; v2 sync cannot discover v1; backup export/import remains compatible; storage migration is explicit and reversible.

### P1. Navigation and wayfinding
- **Confirmed:** App.tsx presents seven top-level nav destinations: Overview, Build, Tree, Train, Play, Check, Games; Settings is an additional icon, while profile/repertoire selectors, undo/redo, sync and analysis share the same top bar.
- **UX hypothesis:** This is dense, especially on narrow screens, and exposes tool names rather than a clear user journey.
- **Recommendation:** Define 4–5 primary areas (Home, Repertoires, Train, Play, Games), with Build/Tree/Check as contextual modes of a selected repertoire. Keep every function discoverable; no removal of capabilities. Consider a desktop sidebar and mobile bottom navigation, with overflow for less frequent actions.
- **Accessibility:** Icon-only actions need consistent accessible labels; review hover-only affordances and keyboard focus.

### P1. Home as a decision surface
- **Confirmed:** HomeView combines greeting, today session, creation, draggable repertoire cards, status metrics, in-play/study toggles, progress and Build/Tree/Train buttons.
- **Recommendation:** Give a single prominent 'Continue training' CTA, a compact daily progress strip, then repertoire cards grouped by white/black or user order. Show only 2–3 high-value metrics per card; expand for secondary data. Surface last-used repertoire and the next meaningful task.
- **Test:** First-time and returning users should identify their next action in under five seconds.

### P1. Training focus
- **Confirmed:** TrainView has separate review and line-practice paths, advanced settings, queue feedback, hints, mistake cards and progress; session view uses board + panel.
- **Recommendation:** Distinguish 'Daily review' from 'Practice a line' at entry, not through dense setup. During a session, prioritize board, move feedback, progress and one primary action; move secondary controls to an expandable tray. Preserve FSRS semantics and feedback timing.
- **Test:** Phone portrait, one-handed controls, keyboard shortcuts and screen-reader announcements.

### P1. Build workspace
- **Confirmed:** BuildView combines chessboard, navigation controls, move bar, saved repertoire moves, annotations, Lichess/Masters/Engine tabs, practice and import actions.
- **Recommendation:** Desktop: resizable or at least predictable board/workspace columns, with contextual data tabs. Mobile: board first, persistent compact move controls, segmented Explorer / My moves / Engine / Notes. Keep save/discard unambiguous and make destructive actions confirmable.
- **Risk:** Do not redesign engine/explorer rendering without checking board geometry and scroll behavior.

### P2. Tree visualization
- **Confirmed:** TreeView has pan/zoom, orientation preference, opening labels, gap ghosts, selection and highlight modes.
- **Recommendation:** Treat it as an advanced visualization; provide a discoverable legend, reset view, search/focus path, and a readable details drawer on mobile. Keep top-down orientation for phones.

### P2. Play, Games and Check
- **Confirmed:** PlayView is particularly feature-rich (Maia, rated runs, time controls, move selection); Games and Check have separate workflows.
- **Recommendation:** Separate 'Quick practice' from 'Rated challenge'; put detailed opponent/time controls in an advanced configuration. Games should lead with review queue and recent games. Check should explain its diagnostic output in plain language and offer direct 'Fix in Build' actions.

### P2. Visual system
- **Confirmed:** styles.css is ~54 KB / 3,331 lines with a mix of root variables, component selectors, media queries and dark-mode rules. Many components also contain inline layout styles.
- **Recommendation:** Before visual restyling, introduce a small token system for color, type, spacing, elevation, border radii, focus and board surfaces. Avoid a full rewrite of CSS at once. Prefer CSS modules or scoped component styles for newly refactored screens.
- **Accessibility:** Test 320/375/768/1024/1440 px widths, 200% zoom, contrast, focus-visible, reduced motion, tap target sizes, and color-independent feedback.

### P2. Quality and delivery
- **Confirmed:** Repository has Vitest unit tests, Playwright E2E config, CI verification and Pages deployment workflows.
- **Recommendation:** Add automated smoke coverage for onboarding, repertoire import, saving a move, train flow, mobile navigation, and backup export/import. Add visual regression screenshots after design approval. Gate deployment on test success.

## Proposed implementation phases
0. **Safety first:** v2 storage + Drive isolation, explicit import-from-v1/backups, PWA identity, tests.
1. **Navigation architecture:** wireframe desktop/mobile, information hierarchy, no removed capabilities.
2. **Choose visual direction:** present three distinct visual concepts before any sweeping visual implementation.
3. **Design tokens + shell:** shared typography, navigation, cards, responsive states, accessible controls.
4. **Home + Train:** highest-impact end-user workflows.
5. **Build + Tree:** power-user workflows; then Play, Games, Check, Settings.
6. **Regression:** full test suite, responsive/device checks, data integrity, PWA offline, sync and backup.

## Three design directions to choose from (not implemented)
- **A. Modern Chess Studio:** charcoal/slate, restrained jade accent, precise information density, strong board-centric layouts. Serious, focused and analytical.
- **B. Warm Editorial:** parchment/off-white, deep ink, muted brass/forest green, spacious typography and restrained diagrams. Distinctive, tactile, premium.
- **C. Live Training Arena:** near-black/navy, crisp lime/cyan status accents, progress and training momentum, more playful but disciplined. Best for active daily use.

Do not implement the visual direction before the owner chooses. Mock up each direction for the same Home and Train screens at desktop and mobile size so the choice is comparable.
